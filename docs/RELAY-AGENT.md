# Relay Agent API v1

Relay Agent — устанавливаемый модуль Light. Он предоставляет IP текущего VPS
как промежуточный узел для PRO: TCP и UDP передаются на фиксированный публичный
IPv4 сервера назначения. TLS пользовательского протокола проходит без изменения;
агент не завершает TLS, не выдаёт VPN-профили и не выполняет произвольные команды.
Сервер назначения видит IP relay; исходный IP клиента не передаётся.

## Подключение

1. В Light, «Обзор → Дополнительные модули», установить Relay Agent.
2. Нажать «Показать параметры PRO» и скопировать JSON подключения.
3. На стороне PRO сохранить `agent_url`, `token`, `certificate_sha256` и `api_version`.
   Токен хранить только на серверной стороне PRO; браузеру возвращать маску.

API слушает HTTPS на `9443/tcp`. Сертификат создаётся на узле, собственный домен
не требуется. PRO должен **проверить SHA-256 DER-сертификата до отправки токена**.
Нельзя отключить проверку TLS без проверки отпечатка. При смене сертификата
подключение блокируется до явного обновления отпечатка владельцем.
Готовый серверный клиент: `protocol-images/relay-agent/client.py`, класс `RelayClient`.
Он не следует redirect и не отправляет токен при несовпадении отпечатка.

Вызовы выполняются из backend PRO, не из браузера. Все endpoints, включая status,
требуют `Authorization: Bearer <token>`. Пароль администратора Light не используется.
Токен можно заменить в Light: старый токен сразу перестаёт работать, listeners и
существующие маршруты сохраняются. Удаление модуля останавливает маршруты и
удаляет токен, сертификат и конфигурацию. Повторная установка/обновление сохраняет
параметры подключения и маршруты, но перезапускает службу relay.

## Контракт

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/v1/status` | Версия, возможности, revision, число слушающих и ошибочных маршрутов |
| GET | `/v1/routes` | Конфигурации, состояние listeners, счётчики текущего запуска |
| PUT | `/v1/routes/{id}` | Создать маршрут с назначенным PRO стабильным ID |
| DELETE | `/v1/routes/{id}` | Удалить маршрут и закрыть его соединения |

PUT принимает только:

```json
{
  "transport": "tcp",
  "listen_port": 20001,
  "target_ip": "203.0.113.10",
  "target_port": 443
}
```

IP в примере документальный: в реальной команде нужен глобальный IPv4.
Нельзя назначать private/loopback/link-local/multicast/reserved IP или IP самого
relay. DNS-имена не принимаются, что исключает DNS rebinding. IPv6 в v1 отсутствует.
ID: 1–64 символа, латинские буквы/цифры/`_`/`-`, первый символ буква или цифра.
TCP и UDP могут использовать одинаковый номер порта независимо.

Перед изменением PRO читает `/v1/routes` и передаёт `If-Match: <revision>`.
Отсутствие заголовка — 428; устаревшая revision, занятый порт или изменение
существующего маршрута — 409. Чтобы изменить маршрут, удалить его и создать
с новой конфигурацией. Не обещать сохранение текущих соединений при замене.

Повторный PUT с тем же ID и конфигурацией возвращает существующий маршрут без
перезапуска и изменения revision. Повторный DELETE отсутствующего ID также
безопасен. При потере ответа сначала читать состояние; токен автоматически
не заменять, а изменяющие команды не повторять вслепую.

`state: listening` подтверждает только listener, а `target_verified: false`
означает, что полный маршрут не проверен. PRO должен отдельно проверять нативный
протокол через `relay_ip:listen_port` с ожидаемым SNI/credentials origin.
Ошибочные listeners после перезапуска отображаются как `failed`; конфигурация
сохраняется, исправление конфликта и перезапуск восстанавливают маршрут.

## Ограничения и эксплуатация

Агент работает отдельным пользователем без root и Linux capabilities.
Допустимы порты `20000–20999`; весь диапазон и порт API резервируются для relay
и открываются установщиком в UFW. Остальные протоколы не могут создавать aliases
в этом диапазоне. Listener не делится с существующим сокетом, открытого proxy
или SOCKS/HTTP CONNECT нет. Максимум 64 маршрута, 128 сессий на маршрут, 32
одновременных запроса API; UDP idle timeout 60 с, TCP idle timeout 300 с.
Счётчики сбрасываются при перезапуске, конфигурации сохраняются атомарно.

При внешнем firewall хостера также открыть `9443/tcp` для PRO и нужные relay-порты
для клиентов. Служба: `vps-control-relay-agent.service`; управление доступно в
разделе «Службы» Light. Обновление агента: кнопка «Обновить агент» в карточке модуля,
использующая установщик из установленного выпуска Light.

Этот контракт подготавливает Light-узел для PRO. Добавление интерфейса реестра
relay и вызовов клиента в PRO выполняется отдельно в `test-pro`.
