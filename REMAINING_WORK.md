## 1. Обязательно до запуска

### 1.1. Проверить Debian 13

Нужны четыре чистых стенда:

| Стенд | Архитектура | Редакция |
|---|---|---|
| L-A | amd64 | Light |
| L-R | arm64 | Light |
| P-A | amd64 | PRO |
| P-R | arm64 | PRO |

На каждом стенде необходимо:

- [ ] установить редакцию через ветку `installer`;
- [ ] проверить запуск API, web и Caddy;
- [ ] выполнить `vps-control status`;
- [ ] выполнить `vps-control verify`;
- [ ] выполнить `vps-control integrity-check`;
- [ ] проверить `/var/lib/vps-control/product.json` и права `0600`;
- [ ] перезагрузить VPS и повторить проверку служб;
- [ ] сохранить журнал установки и обнаруженные ошибки.

Полные команды и ожидаемые результаты находятся в [TEST_PLAN.md](TEST_PLAN.md).

### 1.2. Проверить функциональность Light

- [ ] UI открывается и авторизация работает;
- [ ] доступны только предусмотренные Light возможности;
- [ ] WireGuard устанавливается, запускается и удаляется;
- [ ] AmneziaWG устанавливается, запускается и удаляется;
- [ ] создаётся клиент и импортируется конфигурация;
- [ ] после перезагрузки конфигурации и клиенты сохраняются;
- [ ] в интерфейсе отсутствуют функции PRO и публичная установка test-релиза.

### 1.3. Проверить функциональность PRO

- [ ] сохранена функциональность бывшей ветки `stabl`;
- [ ] Mihomo устанавливается и проходит диагностику;
- [ ] DNS применяется и корректно восстанавливается после ошибки;
- [ ] relay/CDN-домены и маршруты работают;
- [ ] основные прямые протоколы устанавливаются независимо;
- [ ] создание, изменение и удаление профилей не повреждает другие протоколы;
- [ ] настройки и профили сохраняются после перезагрузки.

### 1.4. Проверить production-обновления

Для обеих редакций и обеих архитектур:

- [ ] `vps-control update` выбирает свой production-релиз;
- [ ] выбирается asset правильной архитектуры;
- [ ] полный commit SHA совпадает с опубликованным релизом;
- [ ] обновление не заменяет `product.json` другой редакцией;
- [ ] конфигурации, ключи и клиенты сохраняются;
- [ ] после обновления проходят `verify` и `integrity-check`;
- [ ] намеренно повреждённый релиз вызывает автоматический откат.

### 1.5. Проверить test-релизы

- [ ] скачать CI artifact из `test-light` и установить через `test-update`;
- [ ] скачать CI artifact из `test-pro` и установить через `test-update`;
- [x] выполнить `test-rollback` на L-A для Light;
- [ ] подтвердить, что test workflows не создают GitHub Releases;
- [ ] подтвердить, что test-архив невозможно установить как production-релиз.

### 1.6. Проверить защиту от неверной установки

Работающая версия не должна измениться в следующих сценариях:

- [ ] архив PRO устанавливается поверх Light;
- [ ] архив Light устанавливается поверх PRO;
- [x] test-архив передаётся в `install-release` на L-A;
- [ ] production-архив передаётся в `test-update`;
- [ ] архив `arm64` устанавливается на `amd64`;
- [ ] архив `amd64` устанавливается на `arm64`;
- [ ] metadata или контрольная сумма архива повреждена;
- [ ] повторно запускается установщик с другой редакцией.

### 1.7. Проверить Ubuntu

После успешного прохождения Debian 13:

- [ ] выполнить smoke-test Light на Ubuntu Server 22.04 или 24.04 amd64;
- [ ] выполнить smoke-test PRO на Ubuntu Server 22.04 или 24.04 amd64;

## 4. Критерии завершения MVP

MVP можно считать введённым в эксплуатацию, когда:

- [ ] четыре обязательных Debian 13 стенда пройдены;
- [ ] обе редакции устанавливаются на amd64 и arm64;
- [ ] production и test каналы не смешиваются;
- [ ] неправильные архивы отклоняются без остановки рабочей версии;
- [ ] автоматический откат проверен на практике;
- [ ] Light сохраняет простой WG/AWG-сценарий;
- [ ] PRO сохраняет Mihomo, DNS и relay-функциональность;
- [ ] нет открытых критических и высоких дефектов;
- [ ] `installer` назначен основной веткой.

## 5. Отложено и не блокирует MVP

Эти задачи не нужно включать в текущий цикл стендовых проверок:

- подписка и лицензирование PRO;
- автоматическая миграция Light → PRO;
- перенос настроек между редакциями;
- ручной откат production-версии в течение семи дней;
- интерфейс управления сохранёнными версиями;
- дополнительное подписание релизных архивов;
- расширение списка официально поддерживаемых ОС.

Для каждой из этих функций потребуется отдельный план, реализация и тестирование. Они не должны задерживать проверку и запуск текущего разделения Light/PRO.

## 6. Ближайшее действие

Скачать официальный `test-light` CI artifact с авторизованной GitHub-сессией и повторить короткий test-update/rollback на L-A. Затем повторить Light на Debian 13 `arm64` и перейти к PRO на `amd64`/`arm64`.
